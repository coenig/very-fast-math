- Align --live mode with regular mode:
Yes. --live has grown from an overhead-reduction preset into a separate execution backend. Your original intent is a cleaner boundary: same planner, optional diagnostics and reporting.

What Diverged
Three independent concerns are currently bundled together:

Concern	Current Difference
Output	Live suppresses plots, archives, statistics, overlays, and diagnostic solves. This matches the original intent.
Execution efficiency	Live retains the native library, caches planner translations/preprocessed models, removes launch delays, and uses different timeout handling. These improvements could benefit regular mode too.
Planning policy	Selective checking and persistent solving are restricted to live mode. These need not depend on whether diagnostics are enabled.
Some particularly concrete sources of unnecessary regular-mode overhead:

mc_workflow.cpp:153 sleeps one second per candidate directory before checking whether to launch it.
interactive_testing.cpp:978 makes planner-translation reuse live-only.
interactive_testing.cpp:1027 runs an additional FALSE-specification solve in regular mode.
morty_helper.py:522 retains the native library only for live execution.
Your Configuration Example
There are two separate restrictions in morty.py:96:

Regular mode rejects priority and adaptive.
Both modes reject persistent solving with all.
The second restriction reflects current implementation plumbing: persistent queries are invoked only inside the selective-planning function. It is not an inherent incompatibility between persistent solvers and checking all configurations. Supporting that combination would require an explicit batch implementation.

Also, the error message saying all achieves “equivalent behavior” is misleading. Selective policies change query ordering, early stopping, and shortcut scheduling; they are not merely faster implementations of the same experiment.

Recommended Alignment
I would make one shared planning pipeline, with three independent choices:

Selection: all, priority, or adaptive, available in either mode.
Solver lifecycle: fresh or persistent, subject to supported solver/model capabilities.
Observability: normal experiment outputs versus the lightweight --live preset.
Translation caching, removing artificial delays, and robust timeout/error handling should be shared infrastructure. Full traces, plots, archives, and the extra diagnostic solve should remain output-dependent.

This needs more than deleting the parser checks: selective helpers currently hard-code live=True, regular statistics read runtime files that persistent queries do not populate, and replay assumes archived per-cycle results. Those contracts need aligning so skipped queries are not reported as stale measurements.

Bottom line: your diagnosis is right. Share the efficient execution machinery; keep planning-policy changes explicit; let --live control overhead rather than feature availability.
